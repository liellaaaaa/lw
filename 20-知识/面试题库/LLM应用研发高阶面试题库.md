## 一、RAG 与检索增强（高阶）

**Q1：视觉 Embedding 检索和文本检索在 Milvus 中如何通过 RRF 实现得分归一化？**
- 多路召回分别产出排名列表：视觉向量检索一路、文本 Embedding（Dense）一路、可选 BM25（Sparse）一路。三路打分空间不同，不能直接比较原始相似度。
- RRF（Reciprocal Rank Fusion）公式：`score = Σ 1/(k + rank_i)`，通常取 `k=60`。每一路对同一文档给出排名 `rank_i`，融合后得到统一分数。
- Milvus 中做法：先分别执行各路召回（多 `ANN search`），拿到各自的 top-k 与排名；在应用层按 RRF 公式计算融合分，重排后取最终 top-k。Milvus 2.4+ 的 Hybrid Search 也内置了 RRF/Rerank，但跨模态（视觉+文本）通常需在外部做融合，因为视觉与文本往往使用不同模型、不同 Collection 或不同向量空间。
- 关键点：RRF 用“排名”而非“原始分数”做融合，天然消除了不同向量空间、不同度量方式（cosine / L2 / IP）带来的量纲差异。

**Q2：如何用 Ragas 定位检索环节的语义偏差？**
- Ragas 提供检索侧指标：`Context Precision`（召回文档里有多少与答案相关）、`Context Recall`（答案所需信息有多少被召回）。
- 定位步骤：
  1. 跑评测集，先看 `Context Recall` 低 → 说明“该召回的没召回”，偏向量库覆盖或 embedding 不匹配。
  2. 若 `Context Precision` 低 → 召回了很多无关文档，偏 query 理解偏差或切分/索引噪声。
  3. 结合 `Answer Relevancy` 与 `Faithfulness`：若答案幻觉高且 `Faithfulness` 低，但 `Context Precision` 也低，说明检索侧已带偏模型。
  4. 逐 case 用 LLM-as-judge 对 query-doc 对做相关性打分，定位是“query 改写偏差”“同义术语 gap”还是“chunk 切分切断语义”。
- 工程实践：把低分 case 聚类，看偏差模式（术语不一致、长 query 丢关键词、多义词歧义），再针对性加同义词、微调 embedding、或改 query 改写策略。

**Q3：对于召回的零件图纸，如何通过 VLM 进行结构化推理以减少幻觉？**
- 问题：直接让 VLM“看图描述”容易产生幻觉（尺寸误读、标注漏看、结构关系错判）。
- 结构化推理流程：
  1. **版面分析与 OCR**：先用 VLM / 专用 CV 模型提取图纸中的文本标注、尺寸链、BOM 清单、几何关系，输出结构化 JSON（而非自然语言）。
  2. **schema 约束**：预先定义图纸信息 schema（零件号、材料、尺寸公差、表面粗糙度、装配关系），要求 VLM 按 schema 填充，强制结构化。
  3. **分步 CoT**：第一步“提取关键标注”，第二步“建立尺寸链关系”，第三步“校验一致性（如总尺寸是否等于分尺寸之和）”。每步输出结构化中间结果。
  4. **规则校验**：对 VLM 输出的结构化数据用硬规则校验（如数值范围、单位一致性、必字段缺失检查），不通过则打回重试或人工确认。
  5. **RAG 融合**：将图纸结构化结果入库（向量+结构化字段），后续问答基于结构化数据检索，而非每次都让 VLM 读原始图片。
- 核心思想：把“视觉理解”转为“结构化抽取 + 符号推理”，减少开放式生成的幻觉面。

**Q4：如何通过语义分片解决固定长度切片导致的上下文断裂问题？**
- 固定长度切分（如每 512 token + overlap）容易在句子、段落甚至单词中间切断，导致召回 chunk 语义不完整、前后依赖断裂。
- 语义分片策略：
  1. **边界感知**：优先在句子结束符（。！？）、段落换行、Markdown 标题、HTML 标签处切分，保证最小语义单元完整。
  2. **语义断点检测**：用滑动窗口计算相邻文本块的 embedding 相似度，相似度骤降处视为语义边界（如话题切换），在此切分。
  3. **结构感知**：对 PDF/Word 按逻辑结构（章节、列表、表格）切分；表格尽量整块保留或转为结构化描述后再切。
  4. **动态长度**：设定最小/最大长度区间，在区间内寻找最佳语义边界，避免为了凑长度而硬切。
  5. **上下文增强**：每个 chunk 附加“前情提要”摘要或标题层级，缓解断裂后的上下文缺失。
- 权衡：语义分片实现复杂、切分不均导致 chunk 大小差异大，需配合索引策略（如按 token 计费时做长度截断或分层摘要）。

**Q5：引入 HyDE 进行查询改写时，如何防止生成的伪文档产生幻觉干扰检索？**
- HyDE（Hypothetical Document Embedding）用 LLM 先根据 query 生成“假设的理想答案”，再对假设答案做 embedding 去检索。风险：LLM 生成的伪文档本身含幻觉，会带偏召回。
- 缓解措施：
  1. **混合检索**：HyDE 向量仅作为一路召回，同时保留原始 query 的另一路召回，最后用 RRF 或加权融合，降低单路偏差。
  2. **伪文档校验**：对生成的伪文档做自一致性检查（如多次采样看是否稳定）、或计算其 perplexity，异常低置信度时弃用 HyDE，回退原始 query。
  3. **Rerank 二次过滤**：召回结果用 cross-encoder / LLM reranker 按与原始 query 的相关性重排， HyDE 召回的无关文档可被滤除。
  4. **限制生成长度与风格**：prompt 限制伪文档只基于已知信息风格生成，禁止编造具体事实（如“请生成一段可能包含答案的文档片段，不确定时请留白”）。
  5. **反馈闭环**：记录 HyDE 改写的检索效果，离线评估哪些 query 类型适合 HyDE（如抽象/短 query），哪些不适合（如需要精确实体匹配的 query），动态开关。

## 二、Agent 架构与推理（ReAct / LangGraph / Self-Reflection）

**Q6：讲一下 ReAct 中 Thought、Action 和 Observation 的循环状态机逻辑。**
- ReAct = Reasoning（思考）+ Acting（行动），核心是三阶段循环：
  1. **Thought**：LLM 根据当前目标、历史动作与观察结果，推理“我现在该做什么”。输出自然语言推理过程。
  2. **Action**：基于 Thought，LLM 输出结构化工具调用（函数名 + 参数），由宿主执行。
  3. **Observation**：宿主将工具执行结果返回给 LLM，作为新一轮输入。
- 显式状态机可建模为：`IDLE → THINKING → ACTING → OBSERVING → (判断) → THINKING / FINISHED / ERROR`。
- 状态转移条件：
  - THINKING → ACTING：模型输出有效 Action。
  - ACTING → OBSERVING：工具执行完成并返回结果。
  - OBSERVING → THINKING：结果需进一步处理。
  - OBSERVING → FINISHED：Thought 判断目标已达成，输出最终答案。
  - 任意状态 → ERROR：工具执行异常、超时、或循环次数超限。
- 关键设计：每轮 prompt 必须包含完整的 `Thought_i → Action_i → Observation_i` 历史轨迹，让模型看到因果链；状态机层需管控最大步数、重复检测、预算上限。

**Q7：如果模型发现上一步工具调用的结果不符合预期，如何设计 Self-Reflection 机制触发重新规划？**
- Self-Reflection 是 Agent 从错误中恢复的关键模块，设计要点：
  1. **偏差检测**：在 Observation 返回后，用 LLM（或规则）评估结果是否符合预期。评估维度：schema 是否匹配、业务规则是否满足、是否含错误信息/空结果/异常。
  2. **Reflection 输出结构化**：定义反射结果 schema，如 `{status: "success|retry|replan|escalate", reason: "...", suggestion: "..."}`。
  3. **分级处置**：
     - `retry`：同工具、改参数重试（如日期格式错误、范围过大）。
     - `replan`：工具选错或目标需拆解，回到 Planning 阶段重新生成计划。
     - `escalate`：超出 Agent 处理能力，转人工或降规则兜底。
  4. **重规划（Re-planning）**：若需 replan，保留已成功的中间结果，仅对失败子任务重新生成计划，避免全量重来。
  5. ** LangGraph 实现**：用 conditional edge 从 Observation 节点连到 Reflection 节点，Reflection 节点再决定下一步走向（回 Think 节点、回 Plan 节点、或结束）。
  6. **防循环**：反射次数上限 + 检测“同一错误反复反射”的陷阱状态，强制终止或降级。

**Q8：LangGraph 相比 LangChain 的内置 Chain 在处理策略路由的循环逻辑时有哪些优势？**
- LangChain Chain（包括 `RouterChain`）本质是有向无环图（DAG）或线性 pipeline，节点间关系在定义时基本固定，循环/回退能力弱。
- LangGraph 优势：
  1. **原生支持循环**：StateGraph 允许边从一个节点连回自身或前驱节点，天然实现“策略路由 → 执行 → 观察 → 不满意则重新路由”的闭环。
  2. **显式状态管理**：全局 `State` 对象在各节点间传递，循环时状态自动累积，无需手动拼接 prompt 历史。
  3. **条件边（Conditional Edge）**：根据状态动态决定下一个节点，策略路由逻辑写在 `edge_function` 里，清晰可调试。
  4. **Checkpoint 持久化**：任务中断后可从任意节点恢复，适合长循环任务和人工回环（`interrupt`）。
  5. **内置人机回环**：循环中可插入 human-in-the-loop 节点（如审批、确认），Chain 很难优雅实现。
  6. **多 Agent 编排**：多个子图（subgraph）可组合，循环逻辑可封装在子图内部，上层 orchestrator 只负责调度。
- 总结：Chain 适合“一次性”pipeline；LangGraph 适合“需反复迭代、动态路由、状态持久化”的复杂 Agent 工作流。

**Q9：讲一下 OpenClaw 的记忆实现。**
- 注：OpenClaw 并非业内最广为人知的开源项目名称，此处按“高阶 Agent 记忆系统”的通用工程实现作答。若面试中确指某具体框架，需结合其源码补充。
- 通用高级记忆分层实现：
  1. **工作记忆（Working Memory）**：当前对话窗口的最近 N 轮交互，直接放在 prompt 里，供即时推理使用。
  2. **短期摘要记忆**：当工作记忆超过 token 预算时，用 LLM 对历史对话做渐进式摘要（如递归摘要：每轮把旧摘要+新对话压缩成新摘要），保留关键事实与意图。
  3. **长期向量记忆（Episodic）**：对话中的重要事件、用户偏好、关键结论，提取为“记忆片段”写入向量库。检索时按与当前 query 的语义相似度召回。
  4. **结构化语义记忆（Semantic / 知识图谱）**：用户画像、业务实体关系、持久化事实，存为结构化数据（如 JSON / 图数据库），支持精确查询与推理。
  5. **记忆写入策略**：不是所有内容都存。用 LLM 给每条信息打“重要性分数”和“时效等级”，高分长期保留，低分 TTL 过期；写入前做去重与冲突消解（时间戳优先、或 LLM 仲裁）。
  6. **记忆读取策略**：多路召回（工作记忆 + 摘要 + 向量片段 + 结构化画像），用 LLM 做最终整合，避免简单拼接导致上下文爆炸。

## 三、工具与上下文管理

**Q10：如果工具规模达到上百个，如何设计 Tool Retrieval 来降低上下文压力？**
- 问题：上百个工具的 schema 全部塞进 prompt，token 爆炸且模型选错率飙升。
- 方案：
  1. **工具向量化索引**：把每个工具的 `name + description + 参数摘要` 转成 embedding，构建“工具向量库”。
  2. **两阶段调用**：
     - 阶段一（Tool Retrieval）：根据用户 query 在工具向量库中召回 top-k（如 5~10 个）最相关工具。
     - 阶段二（Function Calling）：仅将这 top-k 工具的完整 schema 塞进 prompt，让模型做选择。
  3. **工具分类与标签**：先按领域/业务做预分类（如“财务类”“HR类”“运维类”），检索时先过滤类别，再在类内向量召回，降低候选空间。
  4. **工具摘要压缩**：对复杂工具参数，先用 LLM 生成“一句话调用摘要”，检索阶段用摘要替代完整 schema，减少向量噪声。
  5. **层次化组织**：大类 → 子类 → 具体工具，类似文件系统目录；Agent 先选目录再选工具。
  6. **缓存热门组合**：对常见任务模式，缓存其常用工具组合（如“报销审批”固定需要查预算+提交单据+通知），避免每次都重新检索。
  7. **动态加载**：支持工具按租户/权限动态子集化，用户只能看到自己有权限的工具，进一步缩小候选池。

**Q11：MCP 在连接外部心理量表工具时，如何定义 Resources 与 Tools 的映射关系？**
- MCP 中 `Resources` 表示只读的数据上下文（如文件、数据库记录、配置），`Tools` 表示可执行的操作（带副作用或计算）。
- 以“心理量表（如 SDS 抑郁自评量表）”为例：
  - **Resources**：
    - `resource://psych-scale/sds/questions` — 量表题目与选项。
    - `resource://psych-scale/sds/norms` — 常模数据（年龄/性别分层标准分）。
    - `resource://psych-scale/sds/instructions` — 测评指导语。
  - **Tools**：
    - `tool://psych-scale/sds/evaluate` — 提交答题结果，计算标准分并返回评估结论。
    - `tool://psych-scale/sds/export-report` — 生成 PDF 测评报告。
- 映射关系设计：
  1. **URI 层级命名**：按 `领域/工具/资源类型` 组织，保证 Resources 与 Tools 在同一命名空间下可关联。
  2. **参数引用**：Tool 的 input schema 中，可用 `resource_uri` 参数显式引用 Resource（如 evaluate 工具接收 `answers` + 可选的 `norm_version_uri`），实现 Tool 对 Resource 的动态读取。
  3. **只读 vs 副作用分离**：量表题目属于静态数据，用 Resource 暴露，可被多个 Tool 复用；评分计算和报告生成带业务逻辑/副作用，用 Tool 暴露。
  4. **权限映射**：Resource 可设置读取权限（谁可见题目），Tool 可设置执行权限（谁可提交评分），MCP Server 在 capability 协商时声明。

**Q12：随着模型上下文扩展到 1M+，你认为外挂的向量记忆库未来会被长上下文完全取代吗？**
- 观点：**不会完全取代，二者将长期互补，分工演变为“长上下文 = 工作记忆，向量库 = 长期记忆”。**
- 原因：
  1. **成本经济性**：1M token 的推理成本远高于向量检索 + 短 prompt 生成，频繁全量加载不现实。业务场景对成本敏感。
  2. **注意力噪声**：上下文越长，模型注意力越分散，无关信息稀释关键信号。精准召回（RAG）能保证上下文高信噪比。
  3. **动态更新**：向量库支持文档实时增删改查；长上下文窗口需重新加载整个文档集合，难以做到“增量更新”。
  4. **多租户与权限**：向量库天然支持 metadata 过滤（tenant_id、角色、权限），长上下文把所有内容混在一个窗口里，隔离成本高。
  5. **检索精度与可解释性**：RAG 召回路径可追溯（哪条文档被引用）；长上下文靠模型“内部记忆”定位，难以审计和调试。
  6. **混合趋势**：未来更可能是“长上下文 + 向量库”混合架构——用长上下文承载近期高频信息（工作记忆），用向量库存储海量历史/知识（长期记忆），检索后精确定位再加载到窗口中。

**Q13：向量记忆库中的用户画像如何随对话动态更新？**
- 用户画像动态更新机制：
  1. **画像 Schema 定义**：结构化字段（基本信息、偏好、目标、禁忌、常用表达风格、历史关键事件），同时保存向量摘要。
  2. **触发时机**：
     - 对话结束/轮数达到阈值时批量更新；
     - 关键信息实时提取（用户明确陈述新事实，如“我下周要去深圳”）。
  3. **Delta 抽取**：用 LLM 从最新对话中提取“信息变更点”（新增、修改、删除），输出结构化 diff，而非全量重写画像，降低幻觉和成本。
  4. **合并策略**：
     - 无冲突：直接追加或覆盖。
     - 有冲突：打时间戳，新信息优先；对重要冲突（如地址变更）可反问用户确认。
  5. **存储形式**：结构化字段存 KV / 关系表（便于精确过滤），非结构化摘要存向量库（便于语义召回）。
  6. **遗忘与衰减**：给信息设 TTL 或重要性衰减（如临时行程一周后失效），避免画像膨胀。
  7. **隐私与授权**：敏感画像字段（收入、健康状况）需用户显式授权才能记录，支持“一键遗忘”某类信息。

## 四、Multi-Agent 系统

**Q14：讲一下 Multi-Agent 分层架构与 P2P 架构的区别。**
- **分层架构（Hierarchical / Orchestrator-Worker）**：
  - 拓扑：星型或树型，存在一个（或多个）中央 Orchestrator 负责分解任务、分配子任务、汇总结果；Worker Agent 负责执行具体子任务。
  - 通信：Worker 之间不直接通信，所有协调通过 Orchestrator。
  - 优点：全局调度清晰、责任边界明确、易做全局一致性控制和审计。
  - 缺点：Orchestrator 单点瓶颈、单点故障风险、复杂调度下 Orchestrator 上下文膨胀。
  - 适用：任务可明确分解、需强一致性的场景（如软件工程：架构师 → 程序员 → 测试员）。
- **P2P 架构（Peer-to-Peer / 去中心）**：
  - 拓扑：网状，Agent 之间直接通信，无中心节点。
  - 通信：Agent A 可直接向 Agent B 发消息协商、请求服务或广播信息。
  - 优点：无单点瓶颈、通信延迟低（无需中转）、适合平等协作、可扩展性好。
  - 缺点：通信复杂度 O(n²)、易出现信息冗余、全局状态一致性难保证、死循环/互相调用风险高。
  - 适用：平等协作、需快速协商、或对抗/辩论场景（如谈判、头脑风暴、红蓝军对抗）。
- **对比总结**：分层像“公司组织架构”，P2P 像“扁平团队群聊”；实际系统可混合（上层分层调度，下层 P2P 协作）。

**Q15：如何优化智能体之间的通信损耗，防止冗余信息导致决策效率下降？**
- 通信损耗主要来自：上下文爆炸（传递全量历史）、自然语言冗余、高频往返、信息重复。
- 优化手段：
  1. **消息压缩与摘要**：Agent 向其他 Agent 发送消息前，先用 LLM 把本地长上下文压缩成“相关摘要 + 关键结论”，只传对方需要的部分。
  2. **结构化通信协议**：不用自然语言闲聊，改用严格 schema（如 JSON：{intent, payload, priority, deadline}），减少歧义和解析成本。
  3. **共享记忆替代广播**：把公共信息写入“共享黑板/记忆池”，其他 Agent 按需读取，变“推”为“拉”，减少重复传输。
  4. **层级过滤**：下层 Worker 只向上层 Orchestrator 汇报状态摘要和异常，细节存本地日志，需要时再去拉取。
  5. **批量通信**：把多个小消息合并为一次批量同步，降低往返次数（尤其 LLM 调用开销高）。
  6. **重要性评分与去噪**：对要发送的信息做重要性打分，低于阈值的信息丢弃或不发送。
  7. **通信预算**：给每个 Agent 设定“每轮最大通信 token/条数”预算，强制精简。

**Q16：如何设计共享全局空间记忆来解决各智能体间上下文理解不一致的问题？**
- 问题：多 Agent 各自持有局部记忆，对同一事实的理解可能不一致（如 A 认为“客户预算 10w”，B 认为是“8w”），导致协作出错。
- 共享全局空间记忆设计：
  1. **中央记忆池（Shared Belief Store）**：所有 Agent 共享一个统一存储，分两层：
     - **事实层（Ground Truth）**：经确认的关键事实（如客户最终确认的预算），带版本和时间戳，写入后不可随意覆盖，更新需“提议-确认”机制。
     - **观察层（Observations）**：各 Agent 的局部观察可写入，但标记来源和置信度，允许暂时冲突。
  2. **读写协议**：
     - 读：Agent 决策前必须读取相关全局事实，作为上下文的一部分。
     - 写：Agent 发现新事实时，先写入“观察层”；重要事实需经 Orchestrator 或共识机制（如多数 Agent 确认、或人工确认）后提升到“事实层”。
  3. **冲突消解**：当观察层出现冲突，由 Orchestrator 或专用 Arbiter Agent 根据时间戳、信息来源权威度、一致性规则做仲裁。
  4. **局部缓存 + 全局同步**：Agent 可缓存全局事实的本地副本，但需定期/事件触发同步，保证最终一致性。
  5. **语义对齐**：全局记忆中的关键概念维护统一术语表（ontology），避免不同 Agent 用不同词汇描述同一事物。

**Q17：针对 Agent 推理链路，如何通过中间节点的轨迹有效性量化模型的表现？**
- 目标：不仅看最终任务成败，还要评估推理过程中每一步 Thought / Action 是否有效、是否冗余、是否高效。
- 量化方法：
  1. **节点有效性定义**：
     - 有效（Helpful）：该节点直接推动任务向目标前进，去掉后成功率下降或步数增加。
     - 冗余（Redundant）：该节点未贡献新信息或新动作，可被移除而不影响结果。
     - 错误（Erroneous）：该节点产生错误 Action / 错误 Thought，导致后续需额外步数纠正。
  2. **反事实评估（Counterfactual）**：对轨迹中的每个中间节点，构造“去掉该节点后的替代轨迹”，对比任务成功率与完成步数，量化其边际贡献。
  3. **轨迹级指标**：
     - **有效节点比例** = 有效节点数 / 总节点数。
     - **步数效率** = 理论最少步数 / 实际步数（越接近 1 越好）。
     - **恢复成功率**：轨迹中出现错误节点后，Agent 能否在后续 N 步内自行纠正并完成任务。
  4. **自动化评估**：
     - 用规则匹配判断 Action 是否空转（如重复调用同一工具、参数未变、返回结果相同）。
     - 用 LLM-as-judge 对 Thought 质量打分（是否切题、是否有新推理、是否重复前文）。
  5. **可视化与归因**：把轨迹画成图，标记红（错误）黄（冗余）绿（有效）节点，帮助定位模型薄弱点（如某类工具总选错、某类场景总绕圈）。
