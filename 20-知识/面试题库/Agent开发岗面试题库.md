## 一、基础问题必会

**1.1 自我介绍怎么讲（Data Agent 岗）？**

- 结构：基本信息 + 项目经历（突出 Agent/后端相关）+ 岗位匹配点。
- 要点：① 1-2 分钟，讲"做了什么、解决什么问题、量化结果"；② 突出与岗位相关的项目（RAG 问答、Agent 应用、工具调用）；③ 表明学习方向与岗位契合。
- 别背简历，讲出技术深度和思考。

**1.2 Agent、ChatBot、RAG 应用和工作流的区别？**

- **ChatBot**：以 LLM 生成文本为核心，多轮对话但无自主行动能力，靠 prompt 引导，不操作外部世界。
- **RAG 应用**：在 ChatBot 上加"检索增强"——先检索知识库相关内容拼进 context 再生成，解决知识时效/幻觉；但仍属"问-答"模式，不做外部动作（除检索本身）。
- **工作流（Workflow）**：用 DAG/固定编排把多个步骤串起来（如 n8n、Dify 工作流），每个节点是确定逻辑或固定 LLM 调用，路径预设、可预测。适合流程固定场景。
- **Agent**：以 LLM 为决策中心，能据环境反馈自主选择工具/动作、循环迭代直到目标达成。核心是"自主决策 + 工具调用 + 反馈闭环"，路径运行时动态决定。
- **一句话区分**：确定性 vs 自主性。工作流路径静态、可预测；Agent 路径动态、LLM 决策。RAG/ChatBot 不主动操作外部系统；Agent 会。

**1.3 Function Calling 和 Agent 的关系？**

- Function Calling（工具调用）是 LLM 的能力：模型输出结构化 JSON 指明调用哪个函数 + 参数，由宿主程序执行。它是 Agent 的"手脚"。
- Agent = LLM（大脑）+ Function Calling（手脚）+ 记忆/环境（感知）+ 控制循环（ReAct 等）。没有 FC，Agent 只能"想"不能"做"；FC 也可脱离 Agent 用于简单结构化抽取（如从文本抽实体），不构成 Agent。
- 关系：Function Calling 是 Agent 的必要能力但非充分条件。

**1.4 ReAct、Plan-Act-Observe-Reflect 的运行逻辑？ReAct 由哪几部分组成、执行流程？（用户给一个问题如何完成）**

- **ReAct**（Reasoning + Acting）：由 **Thought（推理）→ Action（工具调用）→ Observation（观察结果）** 循环 + 最终 **Answer** 组成。
- 执行流程（以用户提问为例）：
  1. 用户提问 → Agent 进入循环；
  2. Thought：LLM 分析问题需要什么信息/工具；
  3. Action：调用对应工具（搜索/查库/执行代码等），带参数；
  4. Observation：工具返回结果，拼进上下文；
  5. 重复 2-4 直到信息足够；
  6. Answer：输出最终答案。
- 关键：每一步的 Thought/Action/Observation 都写入上下文，模型基于完整轨迹继续推理；循环有最大步数/终止条件防死循环。简单通用，但缺全局规划，长任务易迷失。
- **Plan-Act-Observe-Reflect**：
  - Plan：先生成整体计划（任务拆成子步骤）
  - Act：执行当前步骤的工具调用
  - Observe：观察结果
  - Reflect：反思——计划还合理吗？是否重规划？再据反思继续或修正
  - 比 ReAct 多了"规划"和"反思"，适合长程复杂任务，能纠正跑偏，常配合 Re-planning。

**1.5 固定工作流和自主 Agent 如何选型？哪些场景不该用 Agent？**

- 用**工作流**：流程固定、步骤明确可穷举、要求 100% 可预测、合规强、调试成本敏感。例：表单审批流、固定 ETL、模板化报告。
- 用**Agent**：任务开放、路径不可穷举、需据环境动态决策、涉及多工具组合、长程目标。例：线上告警根因排查、非标智能客服、数据探索。
- **不该用 Agent**：① 确定性高/规则明确（if/正则/工作流更稳更便宜）；② 可解释性/审计要求极高且容错低；③ 延迟/成本敏感且任务简单；④ 工具不可靠或外部系统不支持回滚（易重复执行造成副作用）。

**1.6 单 Agent 和多 Agent 分别适合什么任务？**

- **单 Agent**：任务边界清晰、工具集集中、上下文可在一个会话内管理。大多业务场景够用，简单可控。
- **多 Agent**：① 任务可自然分角色（规划者/执行者/审查者）；② 需并行独立子任务；③ 需隔离上下文（不同领域知识互不干扰）；④ 需"对抗/审查"提质量（生成+critic）。例：代码生成（coder+reviewer）、研究（researcher+writer）、复杂编排（orchestrator+worker）。
- 风险：通信开销、状态同步、易形成循环调用（死循环）、调试难。

**1.7 LLM 和 Agent 之间的联系和区别？**

- 联系：Agent 以 LLM 为大脑/决策引擎；LLM 提供推理、规划、理解、生成能力，是 Agent 的核心组件。
- 区别：
  - **LLM 是被动的**：输入 prompt → 输出文本，一次/多轮对话，不主动行动，无环境感知。
  - **Agent 是主动的**：感知环境（Observation）→ 决策（LLM 推理）→ 行动（工具调用）→ 再观察的循环，能自主完成任务。
- 一句话：LLM 是"会说话的大脑"，Agent 是"有手有脚能办事的完整个体"；LLM 可独立用于对话/生成，Agent 必然包含 LLM 但不止于 LLM。

**1.8 接入大模型需要考虑哪些问题？**
- 稳定性：超时、重试、降级、熔断；多模型路由。
- 成本：token 计费、Prompt Cache、预算控制、限流。
- 安全：数据脱敏、权限、防注入、审计。
- 质量：幻觉、输出一致性、评估体系。
- 工程：并发、流式输出、长上下文截断、多租户隔离。

**1.9 Prompt 工程化如何理解？为什么要对 AI 输出结果进行 JSON 约束？如何进行 JSON 约束？**
- Prompt 工程化：把 prompt 从临时文本变成可版本管理、可测试、可复用的工程资产，包括模板化、变量注入、A/B 测试、版本管理、效果评测。
- JSON 约束原因：① 结构化，便于下游程序解析；② 减少幻觉/自由发挥；③ 强制字段完整、类型正确；④ 与工具调用、数据库写入对接。
- 如何约束：① 明确在 prompt 中要求 JSON 格式并给出 schema；② 使用 Function Calling / JSON mode（如 OpenAI `response_format={type:"json_object"}`）；③ 给出 few-shot 示例；④ 后校验（JSON schema 校验、字段类型检查、LLM 二次校验）。

## 二、RAG 不能只背「切分、向量化、召回、生成」

**2.1 多格式文档解析怎么做？**

- 格式覆盖：PDF（文本层 vs 扫描件→OCR）、Word/Excel/PPT、HTML、Markdown、图片表格、LaTeX。
- 工具：unstructured、LlamaParse、Marker、PyMuPDF；扫描件用 PaddleOCR / 商用 OCR。
- 难点：版式还原（多栏、表格跨页、脚注）、公式、图表 caption 关联。建议保留"结构元数据"（标题层级、页码、表格坐标）。

**2.2 语义切分策略有哪些？**

- 固定长度切分（按 token/字符 + overlap）：简单但易切断语义。
- 语义切分：基于句子/段落边界，或用 embedding 相似度检测"语义断点"再切（semantic chunker）。
- 结构感知切分：按 Markdown 标题、HTML 标签、PDF 逻辑结构切，保留层级。
- 选择：长文档用结构+语义混合；代码按函数/类；表格尽量整块保留或转结构化描述。

**2.3 混合检索与重排怎么做？**

- 混合检索：向量（dense）语义召回 + 关键词（BM25/sparse）字面召回，融合（RRF / 加权）。
- 重排（rerank）：用 cross-encoder 或 LLM 对 top-k 候选重打分提精度。
- 流程：多路召回 → 融合 → 粗排 → 重排 → 截断 → 拼 context。

**2.4 多租户权限过滤如何实现？**

- 在 metadata 加 tenant_id / 部门 / 角色，向量库支持 metadata filter（Milvus、pgvector 的 where）。
- 关键：过滤必须在召回阶段生效（pre-filter 优先；检索后剔除会漏召回）。避免无权限文档进 context（越权泄露风险）。

**2.5 召回率低的排查路径？**

- query 与文档表述差异大（术语/同义）→ 加同义词、query 改写（HyDE：用假设答案检索）。
- chunk 切太碎/错位 → 调切分策略。
- embedding 不匹配领域 → 换/微调模型。
- 相似度阈值过高 / top-k 太小 → 放宽。
- 元数据过滤误杀 → 查 filter 条件。
- 索引未更新/文档未进库 → 查 pipeline。
- 用离线评估集（标注 query-doc 相关性）量化召回率，逐环节定位。

**2.6 智能问答知识库的短期记忆和长期记忆怎么做？业界主流 3 层记忆系统？每层存什么？**

- **短期记忆（工作记忆）**：当前会话上下文（system + 多轮对话），随请求一起进 LLM；实现：上下文窗口、对话截断/压缩/摘要。
- **长期记忆（外部存储）**：跨会话持久化——用户画像/偏好/历史事实存 DB 或向量库，按需检索后注入上下文。
- **业界主流 3 层记忆系统**（如 MemGPT/Letta、Zep、LangMem 等）：
  1. **核心记忆（Core）**：常驻 system prompt 的少量关键信息（角色、用户偏好、关键事实）——每轮都在；
  2. **工作记忆（Working/会话）**：当前对话历史 + 推理过程——会话内动态滚动；
  3. **归档/长期记忆（Archival）**：向量库/DB 存的历史知识、经验、用户画像——按需检索召回才进上下文。
- 核心思想：三级分级——常驻最精简、会话动态滚动、长期按需检索（类比人的工作记忆 vs 长期记忆）。

**2.7 RAG 是什么、存什么、分块策略，如何设计一个优秀的 RAG 分块系统？**
- RAG（Retrieval-Augmented Generation）：检索增强生成，先检索相关知识再让 LLM 生成，解决知识时效和幻觉。
- 存什么：原始文档、切分后的 chunk、embedding 向量、metadata（来源、标题、权限、时间等）、重排模型索引。
- 分块策略：固定长度（简单但可能断义）、语义切分（按句子/段落/embedding 相似度断点）、结构感知切分（按 Markdown/标题/表格）、混合策略。
- 优秀分块系统的设计要点：① 保留语义完整性（不切表格/段落）；② 保留上下文关联（parent chunk、层级关系）；③ chunk 大小与 embedding 模型匹配；④ 元数据丰富（便于过滤和溯源）；⑤ 离线评估不同策略的召回率；⑥ 支持多粒度（小块召回 + 大块生成）。

**2.8 AI 没检索到或者短问题没命中怎么办？**
- 根因：query 与文档表述不一致、短 query 信息不足、embedding 语义漂移、top-k/阈值太严。
- 解决：① query 改写/扩展（同义词、HyDE、LLM 生成假设文档）；② 混合检索（向量 + BM25）；③ 重排（rerank）；④ 放宽阈值/增大 top-k 后截断；⑤ 追问澄清（让 AI 反问用户补充信息）；⑥ 兜底策略（承认不知道 + 建议人工）。
- 短问题处理：先做意图识别/实体抽取，把短 query 扩展成更完整的检索句；或利用用户画像/历史会话补全上下文。

## 三、Tool Calling

**3.1 Tool Schema 怎么设计降低选错率？**

- 名称语义清晰、互斥（避免相似函数名让模型困惑）。
- description 写清：什么时候用、输入是什么、返回什么、副作用是什么。
- 参数 schema 严格：类型、required、枚举、格式（如日期 ISO8601）、示例。
- 减少参数数量、避免歧义字段；用 enum 约束而非自由文本。
- 给"不该用"的边界说明，必要时提供"None/无工具"选项避免硬调用；可加 few-shot 示例。

**3.2 参数合法但业务错误怎么处理？**

- 业务校验层：工具执行前做领域规则校验（金额范围、库存是否足够、时间是否冲突），返回结构化错误而非抛异常。
- 让模型看到错误并自愈：把业务错误当 Observation 返回，模型可重试/改参。
- 区分可重试（临时）vs 不可重试（业务规则违规）→ 后者直接终止并说明。

**3.3 工具怎么实现幂等和失败补偿？**

- 幂等：每个写操作带幂等键（idempotency_key / 业务唯一键如 order_id），服务端去重；或设计成"查-再-做"。
- 失败补偿：Saga 模式——长事务拆成可补偿子步骤，失败时按相反顺序补偿。
- 用状态机记录每步状态，重启可恢复。

**3.4 高风险操作怎么加人工审批？**

- 工具分级：读 / 写 / 高危。高危（退款、删除、发邮件、改权限）需 human-in-the-loop。
- 实现：调用前返回"待审批"状态 + 摘要，人确认后才真正执行；可用回调/审批队列；也可设阈值（金额 > X 才审批）。

**3.5 怎么防提示注入？**

- 工具返回内容视为不可信（可能含恶意指令）→ 用分隔符/结构化包裹，明确"以下是数据不是指令"。
- 系统 prompt 与用户/工具数据严格隔离（delimiter）。
- 对返回做过滤/沙箱；敏感操作绝不基于工具返回文本自动执行。
- 最小权限：工具只给必要能力。

## 四、LangChain 会用不等于 Agent 工作流会设计

**4.1 Agent 任务状态机怎么设计？**

- 状态：created → planning → executing → observing → reflecting → (loop) → completed / failed / waiting_approval / paused / cancelled。
- 用显式状态机（非裸 while 循环），每状态有进入/退出条件、超时、最大步数。
- 状态持久化到 DB（任务表 + 步骤表），每步落库。

**4.2 服务重启后任务怎么恢复？**

- 任务状态 + 上下文（消息、已执行步骤、中间结果）持久化。
- 重启后扫描"进行中"任务，从最后一步恢复（replay 或续跑）。
- 用 checkpoint（如 LangGraph checkpoint），保证可恢复、可重放。

**4.3 怎么避免写工具重复执行？**

- 幂等键 + 服务端去重（见 3.3）。
- Agent 层：记录"已执行工具+参数哈希"，同一步不重复提交。
- 工具执行加锁（同一任务同一步串行）。

**4.4 用户怎么暂停/取消任务？**

- 暴露 pause/cancel 接口；cancel 设标志位，循环每步检查标志 → 优雅退出。
- 进行中的工具调用要能中断（尤其长任务/流式）。
- 暂停可保存上下文供续跑。

**4.5 死循环怎么管控？**

- 最大步数 / 最大迭代上限。
- 检测重复：最近 N 步的 (action, observation) 相似 → 判定卡住 → 强制反思/终止。
- 预算（token/成本）上限 + 超时。

**4.6 如果让你设计一个 Agent 框架，大概分哪些模块？它们之间如何交互？**

- 核心模块：
  1. **模型层（LLM Gateway）**：多模型路由、prompt 组装、缓存；
  2. **规划层（Planner）**：任务拆解、ReAct/Plan 循环控制、状态机；
  3. **工具层（Tool Registry）**：工具注册、schema、执行、鉴权、幂等；
  4. **记忆层（Memory）**：短期上下文 + 长期记忆库（见 2.6）；
  5. **知识层（RAG）**：检索、重排、召回优化；
  6. **执行/运行时**：循环控制、超时、步数限制、失败恢复；
  7. **安全与合规层**：权限、审计、防注入；
  8. **观测/评测层**：日志、trace、评估指标。
- 交互：用户 → 规划层拆解 → 模型层推理 → 工具层执行 → 结果回观察 → 循环；全程经记忆层存取上下文、安全层审计、观测层记录。

## 五、MCP 不能只背定义

**5.1 MCP 完整通信模型，以及与 Function Calling、OpenAPI 的区别？**

- MCP（Model Context Protocol）：标准化"LLM 应用 ↔ 外部能力（工具/资源/提示）"的协议。三角色：Host（如 Claude Desktop）、Client（Host 内）、Server（提供能力）。
- 传输：stdio（本地）或 Streamable HTTP / SSE（远程）；JSON-RPC 2.0 帧。
- 生命周期：init（能力协商 capabilities）→ 通信（tools/list、tools/call、resources、prompts）→ 关闭。
- 与 Function Calling：FC 是"模型输出调用意图"的格式约定（厂商相关）；MCP 是"应用与工具服务之间"的传输/协议标准，把工具提供方与模型解耦，可插拔可复用。
- 与 OpenAPI：OpenAPI 描述 REST 接口（给人/代码消费）；MCP 面向 LLM，定义 tools/resources/prompts 的语义 schema + 动态发现 + 双向通信，更适合 Agent 运行时调用。

**5.2 MCP 的认证授权怎么做？**

- Server 侧鉴权（API key / OAuth2 / mTLS）；Client 携带凭证。
- 能力粒度授权（哪些 tool 可用）。注意 MCP 标准对 auth 仍在演进，自建需谨慎。

**5.3 MCP 的安全风险、恶意 Server 与数据外泄？**

- 恶意 Server 可返回带注入指令的结果、诱导 Agent 调用其他高危工具、外泄上下文数据。
- 防护：只连可信 Server；Server 返回内容当不可信（沙箱/过滤）；最小权限；审计 Agent 调用链；出站数据做 DLP。

**5.4 MCP 和 Tool 之间有什么联系和区别？**

- **Tool（工具）**：Agent 能调用的具体能力单元（名称、描述、参数 schema、执行逻辑），是 Agent 的"手脚"。
- **MCP（Model Context Protocol）**：一种标准化协议，定义"工具/资源/提示如何被描述、发现、调用"，解决工具接入碎片化。
- 联系：MCP Server 里暴露的就是 Tool（`tools/list` 发现、`tools/call` 调用）；Tool 是内容，MCP 是组织与传输方式。
- 区别：Tool 是"一个能力"（逻辑/函数）；MCP 是"一种协议/标准"（连接 Agent 与外部工具的通用接口）。没有 MCP 也能用 Tool（直接 function calling）；MCP 让工具可插拔、跨平台复用。

**5.5 了解 Skill 的"渐进式加载（渐进式披露）"机制吗？**

- 概念：把大量技能/指令拆成多个独立 skill 文件，不在系统 prompt 全量加载，而是"**目录 + 按需加载**"——只把技能清单（名称 + 一句话描述）放进上下文，任务需要时再加载对应 skill 的完整指令。
- 好处：① 省 token/成本（不全量常驻）；② 减少上下文噪声、提升专注度与输出质量；③ 可扩展（加新技能不改主 prompt）；④ 触发更精确。
- 类似机制：Anthropic Agent Skills、Claude Code slash commands、Cursor rules、MCP resources。
- 与 MCP 的关系：Skill 侧重"指令/方法论"的渐进式披露；MCP 侧重"工具能力"的标准化接入。

**5.6 Skill 的 md 文件存哪里、内容是什么、如何被检索到？**
- 存在哪里：按项目/技能分类存到文件系统、对象存储或向量库；常按目录组织（如 `skills/{category}/{skill_name}.md`）。
- 内容：skill 名称、触发条件/适用场景、详细指令（做什么、不做什么）、输入输出格式、示例、边界情况。
- 如何被检索：① 构建 skill 索引（名称 + 描述 + 标签）；② 用户 query 来时，用 LLM/embedding 匹配最相关的 skill；③ 只把匹配到的 skill 完整内容加载进 context（渐进式加载）；④ 可结合 metadata filter（权限/分类）。

## 六、安全不是在 Prompt 里写一句「不要泄露数据」

**6.1 RAG 文档 / 网页 / Tool 返回中的恶意指令怎么防？**

- 见 3.5（防提示注入）：数据/指令隔离、不可信内容不触发动作、分隔符包裹。

**6.2 Text2SQL 的 AST 校验、只读限制、成本控制、脱敏？**

- AST 校验：把生成 SQL 解析成语法树，白名单校验——只允许 SELECT，禁止 DROP/UPDATE/DELETE/INSERT、多语句、危险函数。
- 只读限制：数据库账号用只读角色；连接层也限制。
- 成本控制：限制返回行数（LIMIT）、禁止全表扫描（cost 估算）、超时。
- 脱敏：结果集按列策略脱敏（如手机号掩码）；或查询前授权校验。

**6.3 敏感数据进入模型前的识别与脱敏？**

- 识别：正则/规则（身份证、手机号、银行卡）+ NER/分类模型。
- 脱敏：掩码、假名化、tokenization；或"检索时过滤敏感字段"。
- 原则：最小暴露，能不进模型就不进。

**6.4 操作审计、凭证撤销、安全事故处置？**

- 审计：每次工具调用/数据访问记录（who/what/when/参数/结果），可追溯。
- 凭证撤销：凭证集中管理（Vault），可秒级吊销；定期轮换。
- 事故处置：预案（止损 → 隔离 → 复盘 → 补丁）；Agent 异常行为熔断开关。

**6.5 怎么做权限校验？**
- 分层：接口层（token/JWT/API key 认证）、数据层（租户/用户 ID 过滤）、工具层（哪些工具可用）、操作层（高危操作审批）。
- RAG 场景：metadata 中带 tenant_id/role，召回前 pre-filter。
- Agent 场景：工具注册时打权限标签，调用前校验用户角色；敏感操作需二次确认/人工审批。
- 审计：记录谁调用了什么工具、访问了什么数据。

## 七、Agent 评测

**7.1 Agent 需要评测哪些指标？**

- 任务成功率：端到端是否达成目标（人工或自动判定）。
- 工具选择准确率：该调的工具调对没。
- 不必要工具调用率：冗余/无效调用占比（越低越好）。
- 引用正确率 & 事实一致性：答案是否基于检索内容、有无幻觉（LLM-as-judge / 事实核查）。
- 人工接管率：多少比例需人介入（越低越自治）。
- 首 Token 时延、任务完成时间、成本：性能与经济学指标。
- 方法：离线评测集 + 在线 A/B + LLM judge + 轨迹回放。

**7.2 使用 AI 时，应该如何保证输出内容的质量？**

- 输入侧：清晰任务描述 + 约束（格式/长度/语气）+ 示例（few-shot）+ 边界说明（不该做什么）。
- 过程侧：结构化输出（JSON/FC）、思维链引导、自检/反思（先列要点再成文）、多轮校验（critic）。
- 检索侧（RAG）：高质量知识库 + 召回优化 + 引用溯源（让模型基于检索内容作答、可核查）。
- 工程侧：评估集 + 自动化评测（LLM-as-judge、指标）、A/B、缓存/重试、护栏（内容过滤）。
- 本质：质量不是靠"prompt 玄学"，而是靠约束 + 验证 + 迭代的可观测工程。

**7.3 AI 幻觉问题如何解决？**
- 检索侧：RAG 引用溯源（要求模型给出出处）、高质量知识库、混合检索 + 重排提高召回准确度。
- 生成侧：降低 temperature、明确约束（只基于给定材料回答）、Self-check（让模型自检）、多模型交叉验证。
- 工程侧：评测集 + LLM-as-judge、事实一致性检查、人工抽检、限制模型在不确定时回答"不知道"。
- 产品侧：高风险答案人工复核、置信度阈值、用户反馈闭环。

## 八、线上工程题——真正拉开差距的地方

**8.1 SSE 断线重连和断点续传？**

- SSE：客户端监听 onerror 自动重连（EventSource 默认）；服务器带 last-event-id，重连时从断点补发。
- Agent 流式：任务状态持久化，断线后新连接按 task_id 恢复同一任务流（续传，不重跑）。

**8.2 用户停止生成后如何真正取消推理？**

- 前端发取消信号 → 后端中断 LLM 流式（abort controller / 取消 future / 关 SSE）→ 清理后台任务，避免"已停但后台还在烧 token/调工具"。需任务级 cancel 标志 + 各层检查。

**8.3 多模型路由、限流、熔断、降级？**

- 路由：按任务类型/成本/质量选模型（简单用便宜小模型，复杂用大模型）。
- 限流：按用户/租户 token 配额；
- 熔断：某模型失败率高 → 切备用；
- 降级：模型不可用时退回规则/缓存/人工。

**8.4 Prompt Cache、语义缓存与错误命中？**

- Prompt Cache：把稳定前缀（system prompt、长上下文）缓存，降延迟降成本（Anthropic/OpenAI 缓存）。
- 语义缓存：相似 query 命中历史答案（embedding 相似度）。
- 错误命中：缓存键设计不当导致"不同问题命中同一答案"→ 用精确+语义双层校验，设 TTL，命中后校验相关性。

**8.5 Token 预算和租户成本控制？**

- 每任务/每租户设 token 上限、成本上限；超限截断/降级/拒答。
- 监控看板 + 告警；按租户计量计费。

**8.6 Docker 怎么用 / Docker 整个使用的过程？**
- Docker 核心概念：镜像（Image）、容器（Container）、Dockerfile、仓库（Registry）。
- 使用过程：① 写 Dockerfile（基础镜像、依赖、启动命令）；② build 镜像；③ run 容器（端口映射、卷挂载、环境变量）；④ 推送到 registry；⑤ 生产环境 pull 并部署；⑥ 监控/日志/重启策略。
- Agent 项目常用场景：隔离环境、快速部署、多服务编排（docker-compose）、CI/CD 集成。

**8.7 流式输出如何实现？**
- 服务端：LLM 支持 stream 模式，逐 chunk 返回；后端用生成器/异步迭代器把 chunk 推给客户端。
- 传输协议：SSE（Server-Sent Events）或 WebSocket；SSE 更轻量，适合单向推送。
- 客户端：逐字/逐块渲染；处理断线重连、取消生成、错误边界。
- 注意：流式也要支持 cancel，后台任务要及时释放。

**8.8 讲一下 SSE？**
- SSE（Server-Sent Events）：服务器向客户端单向推送文本流，基于 HTTP，自动重连，适合 LLM 流式输出。
- 特点：① 基于 HTTP，兼容性好；② 自动重连（EventSource）；③ 支持 last-event-id 断点续传；④ 文本协议，简单。
- 与 WebSocket 区别：SSE 单向（服务器→客户端），WebSocket 双向；SSE 更简单，适合流式回答。

**8.9 说说你知道的 Linux 常见命令？**
- 文件：ls, cd, pwd, cat, less, grep, find, cp, mv, rm, tar
- 系统：ps, top, htop, kill, df, du, free, uname
- 网络：curl, wget, netstat, ss, ping, ssh
- 权限：chmod, chown, sudo
- 容器：docker ps, docker logs, docker exec
- 文本处理：awk, sed, sort, uniq, wc

## 九、真实事故题

**9.1 Agent 重复退款两次，怎么止损和复盘？**

- 止损：立即熔断该工具、冻结相关账户、联系财务拦截。
- 复盘：根因（幂等缺失 / 重试未去重 / 用户重复触发）→ 加幂等键 + 服务端去重 + 退款前查"是否已退" + 人工审批阈值。

**9.2 文档删除后仍然被 RAG 召回？**

- 根因：删除只删源文件没同步删向量库；或软删除未过滤。
- 处置：删除走"连同向量一并删除"的 pipeline；删后做一致性校验；用 delete_by_metadata 批量清理。

**9.3 新 Embedding 模型上线后召回率突然下降？**

- 根因：向量分布变化、旧索引未重建、相似度度量不匹配（cosine vs dot）。
- 处置：上线前离线评估对比；灰度；旧向量需全量重建索引；监控召回率指标。

**9.4 Agent 显示任务失败，但 OA 工单实际已经创建？**

- 根因：工具执行成功但返回/状态上报出错（超时误判失败、异常被吞）；或任务状态机与实际副作用不一致。
- 处置：工具调用与状态更新原子化；执行结果以"系统真实回查"为准而非模型自报；加最终一致性校验。

**9.5 多 Agent 相互调用形成死循环？**

- 根因：Agent A 调 B、B 又调 A，无终止条件/深度限制。
- 处置：调用深度上限、调用图环检测、全局步数预算、引入 orchestrator 集中调度、超时熔断。

## 十、算法与数据结构

**10.1 搜索旋转数组（局部有序，二分查找）？**

- 题：升序数组在某点旋转（如 `[4,5,6,7,0,1,2]`），找 target 下标。
- 思路：二分——mid 把数组分成两段，**必有一段完全有序**；判断 target 是否在有序段内，决定收缩方向。
- 步骤：
  1. `l=0, r=n-1`；`while l<=r`：`mid=(l+r)/2`，`nums[mid]==target` → 返回；
  2. 若左半有序（`nums[l]<=nums[mid]`）：target 在 `[nums[l], nums[mid])` 内 → `r=mid-1`，否则 `l=mid+1`；
  3. 否则右半有序（`nums[mid]<=nums[r]`）：target 在 `(nums[mid], nums[r]]` 内 → `l=mid+1`，否则 `r=mid-1`。
- 注意：① 允许重复时 `nums[l]==nums[mid]==nums[r]` 无法判断有序段 → 只能 `l++` 跳过（最坏退化 O(n)）；② 边界用 ≤/≥ 要小心。
- 复杂度：无重复时 O(log n)。

**10.2 List 和 Map 存什么，应用场景是什么？**
- **List**：有序可重复，适合按顺序存取、遍历、队列/栈场景。
- **Map（HashMap/Dict）**：键值对，O(1) 查找，适合快速查询、去重、计数、配置存储。
- 选择：需要顺序 → List；需要快速查找/映射 → Map。

**10.3 自动去重用什么数据结构？**
- **HashSet / Set**：O(1) 判重，最常用。
- **Bloom Filter**：空间效率极高，适合大数据预过滤，有低概率误判。
- **位图/Bitmap**：适合范围小、整数型去重。
- **数据库唯一索引**：持久化去重。

## 十一、前端基础

**11.1 HTML/CSS/JS 做什么工作？讲讲对 Vue 框架的理解？**
- HTML：页面结构；CSS：样式布局；JS：交互逻辑。
- Vue：渐进式前端框架，核心：响应式数据绑定（data → view 自动更新）、组件化开发、虚拟 DOM、双向绑定（v-model）、生命周期钩子、组合式 API（Composition API）。
- Vue3 特点：Composition API、Teleport、Fragments、更好的 TypeScript 支持、性能优化。
- 在 AI/Agent 项目中：前端常负责对话界面、流式渲染、文件上传、结果展示。

**11.2 LocalStorage 是什么？**
- 浏览器本地存储，键值对，容量约 5-10MB，持久化（除非手动清除）。
- 特点：同源策略限制、只能存字符串（对象需 JSON 序列化）、同步 API。
- 适用：用户偏好、缓存、token（不建议存敏感信息）。
- 与 SessionStorage、Cookie 区别：SessionStorage 会话级，Cookie 可设过期/自动随请求发送。

## 十二、后端与数据库基础

**12.1 如何设计一个好的数据库（表层面 + 字段层面）？**
- 表层面：① 符合业务实体和关系（ER 建模）；② 适度拆分避免冗余（范式）；③ 考虑查询模式设计索引；④ 预留扩展字段/分表分库空间；⑤ 审计字段（created_at/updated_at）。
- 字段层面：① 选择合适类型（INT/VARCHAR/TEXT/DATETIME/JSON 等）；② 非空约束、默认值；③ 外键与级联策略；④ 避免过度使用 NULL 和大字段；⑤ 枚举用 tinyint 或 varchar 而非无约束字符串。

**12.2 索引是干什么的？为什么索引不能多？**
- 作用：加速查询，把 O(n) 扫描变成 O(log n) 或 O(1) 查找。
- 不能多的原因：① 占用磁盘空间；② 增删改时需要维护索引，降低写入性能；③ 优化器选择困难（索引过多可能选错）；④ 每次查询可能涉及更多索引扫描。

**12.3 数据库事务？**
- ACID：Atomicity（原子性）、Consistency（一致性）、Isolation（隔离性）、Durability（持久性）。
- 隔离级别：读未提交、读已提交、可重复读、串行化；常见问题：脏读、不可重复读、幻读。
- 应用：银行转账、订单创建等需要保证数据一致性的操作。

**12.4 Redis 都有什么功能？**
- 缓存：KV 存储，缓解数据库压力。
- 分布式锁：SET NX EX / Redisson。
- 计数器/限流：INCR、滑动窗口。
- 队列：List（lpush/rpop）、Stream。
- 会话/排行榜/Geo/Bitmap/HyperLogLog。
- 持久化：RDB、AOF。

**12.5 分布式锁是什么？解决什么问题？**
- 解决多进程/多机器环境下共享资源的互斥访问问题（如避免重复下单、定时任务重复执行）。
- 常见实现：Redis SET NX EX、ZooKeeper、etcd。
- 要点：互斥、可重入、防死锁（过期时间）、谁加锁谁释放、看门狗续期。

**12.6 GET 和 POST 区别与场景？**
- GET：请求参数在 URL，长度受限，幂等安全，用于获取资源，可被缓存/收藏。
- POST：参数在 body，长度大，非幂等，用于提交/创建资源。
- 选择：读取用 GET，写入/创建/复杂查询用 POST。

**12.7 HTTP 和 HTTPS 是什么及区别？其中 S 代表什么？**
- HTTP：超文本传输协议，明文传输，不安全，默认端口 80。
- HTTPS：HTTP + SSL/TLS，加密传输，防窃听/篡改/冒充，默认端口 443。
- S = Secure（SSL/TLS 安全层）。过程：TCP 连接 → TLS 握手（证书校验、密钥协商）→ 加密通信。
