# AI 集成策略：三种模式与选择

> 一句话总结：业务工具集成 AI 不是"用不用"的问题，而是"怎么用"——纯 AI、AI 优先降级兜底、纯确定性程序，三种模式各有适用边界。选错模式 = 白费力气。

## 为什么写这篇

从入职到现在做了 4 个自研工具，每个都涉及"AI 在什么位置介入"的决策。踩过坑（开票明细工具 Skill 输出不稳定）、找对过路（报价单生成器非结构化输入走 Skill）、也迭代出了中间路线（shippiing_helper PI 解析 AI 优先 + Regex 降级）。这篇笔记把三种模式系统化，作为后续项目的决策参考。

## 三种模式总览

| 模式 | 核心思路 | 典型项目 | 适用场景 |
|------|---------|---------|---------|
| **纯 AI（Skill / API）** | AI 理解意图 → 执行 → 输出 | 报价单生成器 | 输入非结构化、需要语义理解、输出可弹性 |
| **AI 优先 → 降级兜底** | AI 先处理，失败/低置信度时降级为确定性方法 | shippiing_helper PI 解析 | 输入半结构化、准确率要高但容许偶尔降级 |
| **纯确定性程序** | 全程规则引擎，AI 不参与运行时 | 开票明细工具 | 输入结构化、规则可穷举、零容错 |

> ⚠️ **2026-09-04 修正**：Tax_check 曾是本模式的典型案例，**已被推翻**。实际结果是"程序版（html + 轻量 OCR）识别效果很差且不准确"，最终转向 Skill（大模型识别）。详见下方「模式三」案例 2 与「跨模式共性经验」第 6、7 条。

## 模式一：纯 AI（Skill / API 调用）

### 什么时候选

- 输入是**非结构化文本**（微信消息、邮件、自由格式）
- 需要**语义理解**（"客户想表达什么"）
- 输出可以**弹性**（不要求每次完全一致）
- 交互可能是**多轮**的

### 实践案例：报价单生成器

业务员发来微信消息（格式不固定），需要生成格式化 Word 报价单。

```
业务员消息（非结构化）
    ↓ AI 解析意图（正则提取"字段：值"）
    ↓ python-docx 模板填充
    ↓ 输出 .docx
```

- AI 的角色：理解消息意图、提取结构化字段
- 确定性部分：模板填充（`{{占位符}}` 替换、表格填充）
- 关键：**AI 负责"理解"，代码负责"执行"**

### 注意事项

- 输出不稳定是 AI 的天性，如果业务要求每次结果完全一致，考虑降级到模式二或三
- Skill 模式需要 AI 环境依赖（WorkBuddy / API Key），部署门槛高于纯程序
- 详见 [[报价单生成器-Skill制作笔记]]

## 模式二：AI 优先 → 降级兜底 ★推荐

### 什么时候选

- 输入是**半结构化**（有一定规律但不完全固定，如 PI 文件、报关单据）
- 准确率要求**高但不要求 100%**（偶尔降级可接受）
- 已有**确定性方法但准确率不够**（如 Regex 对复杂格式无力）
- 希望**最大化 AI 优势同时保证可用性**

### 实践案例：shippiing_helper PI 解析

PI（Proforma Invoice）文件格式多样（.xlsx/.xls/.pdf），传统 Regex 匹配对非标格式准确率低。7/20 接入 DeepSeek AI 后，采用"AI 优先 → 降级 Regex"策略。

```
用户上传 PI 文件
    ↓ 优先调用 DeepSeek AI 自动识别字段
    ↓ AI 成功 → 返回结构化数据（准确率高）
    ↓ AI 失败/超时 → 自动降级为 Regex 匹配（保底可用）
    ↓ 统一输出到下游流程
```

- AI 的角色：处理复杂/非标格式，提升整体准确率
- 降级机制：AI 不可用时自动回退到 Regex，保证服务不中断
- 关键：**AI 负责"提精度"，确定性方法负责"保底线"**

### 实现要点

1. **统一接口**：无论 AI 还是 Regex，输出格式必须一致，下游不感知差异
2. **降级触发条件**：API 超时、返回格式异常、置信度低于阈值
3. **可观测性**：记录每次请求走的是 AI 还是降级，便于后续优化
4. **渐进式增强**：先有 Regex 保底，再加 AI 增强——不要反过来

### 与纯 AI 的区别

| 维度 | 纯 AI | AI 优先 + 降级 |
|------|-------|--------------|
| AI 不可用时 | 整个功能不可用 | 降级为确定性方法，功能仍可用 |
| 准确率 | 取决于 AI | AI 在线时高，降级时维持基线 |
| 开发成本 | 低（只写 AI 调用） | 中（需同时维护 AI + 降级逻辑） |
| 适合场景 | 新功能、原型 | 生产环境、已有确定性方法的项目 |

## 模式三：纯确定性程序

### 什么时候选

- 输入是**结构化文件**（固定格式 Excel、标准 PDF）
- 规则**可穷举**（列映射、公式计算、格式转换）
- **零容错**（财务数据、合规数据，任何偏差不可接受）
- 部署要求**零依赖**（双击即跑）

### 实践案例 1：开票明细工具

从 ERP 导出的对账单（25 列 Excel）按业务规则转换成开票明细。第一版做成 Skill（AI 驱动），结果输出不稳定；第二版改成纯 HTML+JS（SheetJS），所有规则写死在代码里。

### 实践案例 2：Tax_check 退税审核 —— ⚠️ 反面案例（2026-09-04 修正）

按文件名关键词 + OCR 内容判定单据类型，按价格条款矩阵判断必传单据是否齐全。全程规则引擎，AI 不参与运行时决策。

**结果：这条路走不通。** 程序版（html + 轻量 OCR）识别效果很差、也不准确，最终转向 **Skill（大模型多模态识别）**，效果明显变好且更准确。原因正是旧方案在**扫描件模糊、印章遮挡、ZIP 乱码、跨文档对账**上会失效。该项目 08-12 的 P2 阶段已正式以 Skill 替代原 OCR + 关键词方案。

**错在哪**（详见 [[决策日志]] 与 [[2026-09-04_什么是产品sense_怎么培养|产品 sense 复盘]]）：

当时的判断链是"**只是提效一个人 → 不应该上复杂的程序 → 选轻量方案**"。这里的错误不是"轻量 vs 复杂"，而是**用受益人数去推算技术难度**——这两个维度不能互相折算。

- 受益人数 / 价值规模 → 只决定**投入上限**（值得花几天还是几周）
- 任务本身的难度（版式多样性、精度要求、边界噪声）→ 决定**技术路线可行性**

- 关键：**规则明确时，确定性 > AI 推断** —— 但前提是**规则真的能穷举**（见下面第 6 条"穷举幻觉"）
- 详见 [[开票明细工具-迭代笔记]]

### 注意事项

- "纯确定性"不意味着不能用 AI **开发**——AI 辅助写代码很高效，但运行时不让 AI 做决策
- 纯静态 HTML 工具的优势：零安装、零部署、双击即跑（Tax_check 和开票明细工具都验证了这条路）

## 决策流程图

```
【前置 0】拿 10~20 份真实样本做最小验证（2026-09-04 新增，半天内可完成）
  └─ 记录：准确率多少？失败集中在哪类样本？调参能解决还是方案不行？
     这一步能挡掉 Tax_check 式的整条路线走偏

问：输入是否结构化？
├─ 否 → 需要语义理解？
│   ├─ 是 → 模式一：纯 AI（Skill / API）
│   └─ 否 → 考虑结构化输入预处理后再决策
└─ 是 → 问：规则是否可穷举？（⚠️ 必须分别问输入端和输出端）
    ├─ 否（半结构化，格式多变）→ 模式二：AI 优先 + 降级兜底
    └─ 是 → 问：容错要求？
        ├─ 零容错 → 模式三：纯确定性程序
        └─ 可接受弹性 → 可选模式一或二（看是否需要 AI 提精度）
```

> ⚠️ 选模式时**不要用"受益人数/投入产出比"倒推技术难度**。那是投入上限的判断，不是路线可行性的判断。

## 跨模式共性经验

1. **AI 辅助开发 ≠ AI 驱动执行**：用 AI 写代码很高效，但运行时决策要谨慎
2. **先有保底再上 AI**：模式二的精髓是"确定性方法保底 + AI 增强"，不要反过来
3. **统一接口设计**：无论走 AI 还是确定性方法，下游接口必须一致
4. **轻量工具优先纯静态**：零安装零部署，HTML+JS 或 Python 打包 .exe
5. **数据不出境**：敏感数据（财务、退税）走本地程序，不调外部 API
6. **警惕"穷举幻觉"**（2026-09-04 新增，来自 Tax_check 打脸复盘）：看起来能穷举 ≠ 真的能穷举。单据类型（16+ 种）和价格条款矩阵（4 种）看起来都有限，于是判断"规则可穷举 → 纯确定性程序"；但**规则穷举的是输出端，输入端的版式和噪声是无穷的**。以后判断这条时，必须**分别问输入端和输出端**，只看输出端会得出错误结论。
7. **抽取/识别类任务，默认优先试大模型**（同上）：传统 OCR 只解决"看清字"，不解决"理解含义"。只要样本存在扫描件模糊、印章遮挡、版式不统一、需要跨文档对账，就别指望规则 + 传统 OCR 兜得住。
8. **选路线前先做 10 份真实验证**：成本半天，能避免整条路线走偏。这是把决策流程图"前置 0"落地的具体做法。
