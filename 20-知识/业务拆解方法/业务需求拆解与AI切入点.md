# 业务需求拆解与 AI 切入点判断

> 基于采购分析助手（2 个月开发）和 shipping-helper（2 个月开发）两个完整项目的实战经验提炼。

## 一句话说明

如何把业务部门的一句"我想要……"拆成可控的开发阶段，并判断哪些节点适合用 AI 提效。

## 核心结论

业务需求拆解的核心原则：**先跑通最小数据链路，再叠 AI 能力**。不要一上来就上 AI——先用确定性规则跑通数据流，AI 作为最后一步的准确率放大器接入。

## 拆解方法：四步法

### 第一步：识别"数据从哪里来"

问业务三个问题：
- 你现在每天打开的第一个文件/系统是什么？（数据入口）
- 数据当前以什么形式存在？（Excel/PDF/网页/手工录入）
- 有哪些数据源需要合并？（采购：多数据源价格 + 品类；船务：销售订单 + PI合同 + 产品知识库）

**教训**：shipping-helper 的"三数据源合并"是整个系统最难的部分——订单表、PI合同表、PI合同文件三个格式各异的数据源要在台账层统一。这个环节占了总开发量的 30%+。

### 第二步：定义"最小可用的数据流"

在上一堆功能之前，先把一条完整的数据链路跑通：
- 采购：爬虫取数 → 入库 → 看板展示（5/4-5/8，5 天跑通）
- 船务：订单粘贴 → PI解析 → 数据合并 → 台账（5/28-6/1，5 天跑通）

**判断标准**：如果业务用户不能用这条链路完成一次完整的操作，就不要进入下一阶段。

### 第三步：判断 AI 切入点

| 信号 | 适合 AI | 不适合 AI |
|------|---------|-----------|
| 数据存在但格式不统一 | ✅ PI文件解析接入 DeepSeek | - |
| 规则明确且稳定 | - | ✅ 包装计算（纯数学公式） |
| 需要语义理解 | ✅ MSDS成分翻译、报关品名匹配 | - |
| 结果需要 100% 准确 | - | ✅ 币制字段、HS编码 |
| 模糊匹配/别名映射 | ✅ 成分名别名匹配 | - |

**关键教训**：shipping-helper 的 PI 解析在 7/20 才接入 DeepSeek AI，此前两个月的 Regex 方案始终有识别错误。但 Regex 方案的价值在于**先把数据流跑通了**，AI 来的时候只需要替换解析层。

### 第四步：持续交付节奏

```
Phase 1（1周）：最小数据链路 → 业务试用
Phase 2（2-3周）：文档/报表自动化 → 业务正式使用
Phase 3（持续）：AI 增强 + 边界优化 → 进入维护
```

**两个项目的共同节奏**：
- 采购：4/30 启动 → 5/8 最小链路 → 5/29 交付 → 6月持续优化
- 船务：5/28 启动 → 6/1 最小链路 → 6/22 交付 → 7月持续优化

都是约 1 个月到交付、再 1 个月打磨的节奏。

## 前置环节：业务理解三环节（搭框架 → 填内容 → 复述确认）

> 2026-09-10 并入，源自呱尔德《如何快速理解新业务？》+ 本人船务 TT 助手实战对照。四步法回答"拿到需求后怎么拆"，三环节回答"见业务之前怎么把业务本身看懂"——顺序上三环节在前。

### 0. 为什么要先"看懂"再"拆解"

大多数公司的业务是一地鸡毛：每个人只清楚自己岗位那一亩三分地，能串起来的人很少。宏昊正处于制造业扩张、找提效点的阶段，这个问题尤其典型——单据、数据源、字段映射散落在本地电脑和各人脑子里，不在统一平台上。**需求访谈听不懂业务黑话，根因就是没先看懂流程。**

TT 助手教训：第一次对接船务部，根本听不懂他们在说什么——这个单据、那个数据源、字段映射和对应关系全靠脑补。正确做法是**直接站在业务身边，看他们把整个流程跑一遍**，记录先做什么后做什么；哪怕有些步骤实际是并行的，也先按线性固化下来，梳理出 SOP，再考虑怎么实现。先有流程基线，才能谈优化。

### 1. 搭框架：2-3 天列出大框架再填充

- 先翻文档看重点：核心业务是什么、链路上下游是谁、数据从哪来到哪去、关键指标是什么。
- 带着框架去访谈，防被带偏；**前期不追细节**——"数据流转到下游的条件是什么"这种细节以后迟早会知道（不知道就喜提 bug）。

### 2. 填内容：访谈质量控制四习惯

1. **先找干活的人，别先找领导**。领导讲的是纸面标准流程，一线讲的是实际在跑的流程——**两者的差值就是需求所在**。
2. **同一问题至少问两个人**。单人经验可能漏东西，交叉验证后再定方案；只信一个人的话，上线后大概率要批量返工改。
3. **笔记区分"事实"和"对方认为的事实"**，标注可信度（已确认 / 待验证 / 单人观点）。"这个功能没人用"往往只是"我和我身边的人没用"。
4. **当天聊完当天整理**，哪怕只花 15 分钟拉要点。记忆衰减比想象快，一天聊两三个人信息会互相打架。

心态：理解阶段目标是"懂"，不是"评判"。看到蠢流程先忍住——背后可能是历史原因和资源限制。（但这条对过了新人期的人要警惕：有时候流程蠢就是蠢，别拿"历史原因"当永久借口。）

### 3. 复述确认：讲出来 + 确认单冻结范围

用自己的话把业务串讲一遍，找最懂业务的老员工纠偏——**讲不通的地方就是没理解的地方**。问"我的理解对不对"而不是"这业务是啥"，对方修正成本低才愿意帮。

落地到内部工具开发，复述确认可以升级成**确认单机制**（TT 助手经验）：

- 把理解 + 本期开发范围写成一张单子让业务确认；
- **明确开发到某个点就停住**——这是本期范围；
- 新需求一律进排期，当前阶段只修 bug，不直接接新功能。

这条和四步法的 Phase 节奏是一体的：Phase 切换点就是确认单签字点，防止范围无限膨胀。

## 使用场景

- 业务部门提出一个新的"能不能做个工具"需求时
- 评估一个需求是自己开发还是推给供应商
- 规划一个新工具的开发阶段

## 判断标准

**适合自己开发的条件**（同时满足）：
- 数据不出境 / 本地化要求高
- 业务逻辑复杂但规则明确
- 用户数少（10 人以内），不需要复杂的权限体系
- 你能在 1 周内跑通最小数据链路

**适合推给供应商的条件**：
- 需要多租户 / 复杂权限
- 需要移动端 / 多端适配
- 需要长期运营维护

## 适用边界

- 适用于"面向业务部门的内部工具"场景
- 不适用于面向外部客户的产品开发
- 拆解方法对数据处理类工具尤其有效，对纯 UI/交互类工具参考价值有限
