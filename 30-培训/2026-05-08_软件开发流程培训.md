# 小团队（2–5人）软件开发流程培训

**日期**：2026-05-08 ｜ **培训人**：肖聪（AI技术专员） ｜ **学员**：技术团队 / 供应商协作方 ｜ **适用**：2–5 人小技术团队
**来源**：桌面导出《团队与培训/260508软件开发》（开发流程.md 精简版、软件开发流程梳理详细版.md）

## 一、培训目标
为小团队（含供应商协作）建立从需求到上线的**轻量规范**，砍掉过度设计，先跑通最小闭环，再逐步加自动化。核心原则：**小步快跑，拒绝为了流程而流程**。

## 二、整体流程框架
**精简版四步（小团队直接照做）**：需求确认 → 快速设计与开发 → 交叉测试 → 部署上线（持续迭代回到需求）。

**详细版四阶段关键控制点**：
1. **需求与规划**：必须让提需求的人**书面确认**（防扯皮）；任务拆解成功能列表 + 工时评估 + 迭代计划表；用看板（待开发/开发中/待测试/已完成）可视化。
2. **设计与开发**：**数据库设计必须先行**（定表结构字段，避免后期频繁改库）；前后端分离必须先有接口文档（Apifox/Swagger/YApi）；**必须用 Git**（严禁代码只存个人电脑）；合并前做 Code Review（重点审核心业务逻辑和数据库操作）。
3. **测试与验收**：**交叉测试**——张三开发的功能由李四测（谁开发谁不测该模块）；主流程跑通 + 异常数据不崩；邀请业务方 UAT 确认方可上线。
4. **部署与维护**：**固定上线窗口**（建议周四晚 / 周五下午，方便排查）；小团队用停机更新即可，不需要蓝绿 / 金丝雀；基础监控（CPU/内存/磁盘 + 应用日志）能定位到哪行报错即可。

## 三、Bug 优先级（响应时效）
| 优先级 | 定义 | 响应 |
|---|---|---|
| P0 | 系统崩溃、数据丢失 | 立即，2 小时内修复 |
| P1 | 核心功能失效 | 4 小时内 |
| P2 | 非核心功能 Bug | 1 个工作日内 |
| P3 | 界面 / 体验问题 | 下个迭代 |

## 四、开发模型怎么选
| 模型 | 适用 | 一句话 |
|---|---|---|
| 瀑布 | 需求稳定大型项目 | 阶段清晰但灵活性差 |
| 敏捷 | 需求不确定、快速变化 | 小步迭代、持续交付（小团队首选） |
| DevOps | 追求快速交付+高质量 | 自动化程度高，但需技术积累 |

## 五、给技术负责人的四条落地建议
1. **拒绝口头需求**——再小的需求也要落到文字 / 看板，否则永远做不完。
2. **先跑通最小闭环**——别追求完美架构，先让"需求-开发-测试-上线"转起来。
3. **固定沟通节奏**——每天 10 分钟站会（昨天做了啥 / 今天打算做啥 / 卡在哪）。
4. **控制供应商交接**——要接口文档和数据库设计，逐步接手核心模块，目标 13 周+ 脱离供应商自主运维。

**阶段性目标**：第 1 月建流程 + 交 1–2 个小功能；第 2 月完善规范 + 中等复杂度功能；第 3 月团队磨合具备独立开发能力；第 4 月起脱离供应商。

## 六、上线前检查清单（可直接复用）
- [ ] 代码已完成 Code Review
- [ ] 主流程（冒烟测试）通过
- [ ] 已在测试环境验证通过
- [ ] 已备份当前数据
- [ ] 已确认回滚方案
- [ ] 已通知相关人员和业务方
