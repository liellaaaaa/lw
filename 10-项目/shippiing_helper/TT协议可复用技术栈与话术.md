## 一、可复用的一段话（需求池判断话术）

> **当业务部门提出"想做个工具把某项重复工作自动化"时，若命中以下特征，即可复用 TT 协议（船务助手）已验证的技术栈快速搭建，不必另起炉灶：**
>
> ① 业务规则明确但散落在 Excel / Word / PDF；② 内部用户少（≤10 人）但操作高频；③ 数据敏感、不出境；④ 需多数据源合并；⑤ 需反复生成单证 / 报表。
>
> **典型长相**：已有 SOP 但靠人肉执行，每天 / 每单重复"录入 → 计算 → 生成文档"。
>
> **投入**：1 名全栈 + 1 名业务接口人，1 周跑通最小数据链路 → 2-3 周单据自动化 → 持续 AI 增强。

这段话可直接作为需求池「同类需求识别标准」或向领导汇报时的标准表述。

## 四、何时不套这套（反向信号）

## 五、复用这套技术栈时必须继承的坑：粘贴解析（2026-09-04 实战沉淀）

> **日期**：2026-09-04（船务助手生产环境故障排查，耗时一整个上午）
> **为什么写进本文**：「从 Excel / 企微表格粘贴数据」是这套技术栈最高频的入口（TT、采购、财务、客服场景都一样）。复用技术栈时，这个坑会一起被复用——所以清单和调试方法要跟代码一并交付，不能只给代码。

### 5.1 事故复盘：企业微信表格粘贴导致整表解析失败

**现象**：船务部反馈"销售订单表解析不了"，页面提示「销售订单表未解析到数据」；后台看解析流程没有任何报错。

**根因链**：

1. 从企业微信**在线表格**复制数据时，若单元格内本身含换行（多行文本），复制后一行数据会被截断成多行
2. 第一行销售订单数据在 `WA251` 处断开：原始 15 列 → 变成 `第 1 行 7 列` + `第 2 行 8 列`
3. 行合并逻辑的三个条件**全部要求"前一行 ≥ 10 列"**，只有 7 列的前一行三个条件都不命中
4. 于是两个片段都被当成独立数据行，都缺 `order_no`（第 1 列）和 `internal_code`（第 9 列）→ 全部跳过 → 返回空订单列表 → 前端显示"未解析到数据"

**修复**：补上"两个不完整片段行合并"分支（两行都 < 10 列、但合并后 ≥ 10 列时直接拼接）；行首为空白的行自动补齐空首列。

### 5.2 为什么这么难查（五条，可直接当排查 checklist）

| # | 陷阱 | 具体表现 |
| --- | --- | --- |
| 1 | **本地无法复现 ≠ 代码没问题** | 本地用脚本和 Playwright 测了 Tab 分隔、空格分隔、多行文本、SPA 模式，全部成功——因为构造测试数据是把 15 列写成一个完整字符串，**天然没有截断** |
| 2 | **截断点完全不可见** | 用户看到的粘贴内容就是"正常的两行数据"，没有特殊标记、没有报错，肉眼看不出第 1 行在第 7 列就断了 |
| 3 | **错误信息误导性极强** | "未解析到数据"暗示"格式不对 / 解析器有 bug"，把人引向分隔符检测、列映射、strip/rstrip 等方向；**真正该报的是"第 1 行只有 7 列（应为 15 列），无法识别订单号"** |
| 4 | **多个假设都能自圆其说，但全错** | 排查中产生的假设：strip 丢弃空首列（是真 bug，但已修复且不影响此数据）、8 列行合并后丢列（是真 bug，但不触发此场景）、build 过旧（排除）、前端事件没触发（排除）。每个都值得深挖，都不是根因 |
| 5 | **突破口来自服务器原始响应** | 最终定位靠让用户直接贴出服务器 API 的原始 JSON——看到 `raw_data` 只有 7 个元素时一切清晰：**数据在粘贴时就断了，不是解析器处理时出的问题** |

### 5.3 核心教训（一句话）

> **调试的第一步应该是拿到实际的请求 / 响应数据，而不是在本地猜测复现。本地无法复现 ≠ 代码没问题，很可能是输入数据不同。**

展开成三条可执行动作：

- **面向一线用户排查，第一步就要原始数据**：让用户抓 F12 Network 的请求体或 API 响应，而不是自己先写脚本试。这次如果一开始就拿到，能省掉大半个上午
- **测试样本必须从真实场景取样**：要用户真实"复制粘贴"出来的文本，不要手敲理想字符串。**粘贴本身就是一道隐式加工**（插入换行、转换分隔符），手敲会绕过它
- **假设要写下来逐个证伪**：这次 4 个假设都在脑子里转，每个都合理、都值得查。写下来才能系统排除，也避免"查了半天发现自己早就排除过"

### 5.4 防御设计清单（粘贴解析类功能直接套用）

复用这套技术栈做"从表格粘贴数据"的功能时，下面 6 条应作为**默认要求**而非优化项：

1. **校验前置**：列数不等于预期时直接报「第 N 行只有 X 列（应为 Y 列）」，不要笼统报"未解析到数据"
2. **错误信息指向数据，不指向结果**：说清哪一行、少了几列、缺哪个关键字段
3. **行合并逻辑要覆盖"两个都不完整的片段"**：不要只处理"前半完整 + 后半残缺"
4. **保留原始文本回显 / 诊断面板**：让用户能看到系统实际收到的行数与列数分布
5. **解析结果带诊断信息返回**：附上原始行数、跳过行数、跳过原因，便于远程定位
6. **粘贴来源纳入测试矩阵**：企微在线表格 / Excel / WPS / 网页表格 / 纯文本，每种的分隔符与换行行为都不同

### 5.5 排障 SOP（下次直接用）

1. **拿原始输入**：粘贴文本原文 + 服务端 `raw_data`，不要只听现象描述
2. **对比列数**：预期列数 vs 实际列数 → 判断是"断行"还是"列错位"
3. **本地复现不了，就回去要真实数据**——不要再猜第 5 个假设
4. **定位后双补**：改逻辑 + 补防御性校验与错误信息。只改逻辑不改进提示，同类问题会换个样子再出现

## 六、可复用的实现模式（8 个已验证范式）

> 第二章是"用什么"，这一章是"怎么用"。8 个模式全部来自本项目 5 个月的真实演进，每条都标了触发它的具体事件——复用时可直接判断要不要照搬。

### 6.1 模板占位符 + 行数动态扩展（文档生成）

- **场景**：单据格式固定但条目数不定（报关单 / 发票 / 箱单 / 合同）
- **做法**：模板只放占位符，程序按数据填充；行数按产品数动态扩展；公式引用随扩展重算
- **踩过的坑**：报关单最初硬限制 6 个产品（0803 反馈），8/4 改成动态扩展；8/14 又发现发票页、箱单页同样要扩展，且合同页公式引用不会随扩展重算——**同一个问题藏在四个地方**
- **复用提示**：任何"表格类单据"从第一行代码起就按"行数可变"设计。固定上限一定会在第 N+1 个条目时翻车

### 6.2 多源合并 + 差异比对（数据整合）

- **场景**：同一业务对象散落在多个来源（本项目：销售订单表 + PI 合同表 + PI 合同文件）
- **做法**：统一解析 → 按主键关联 → 合并预览 → 人工确认 → 落库
- **关键设计**：合并预览必须带**来源标记 + 颜色高亮**（仅 PI 橙色 / 仅 SO 蓝色），否则用户不敢信；排序按业务主表优先（8/14 从 SO 优先改为 PI 合同表优先）
- **复用提示**：三源合并的价值不在"自动合并"，而在"把差异摆出来让人确认"。**预览页的可信度 ≈ 采纳度**

### 6.3 AI 优先 + 规则降级（AI 集成模式）

- **做法**：PI 字段提取优先调 DeepSeek 语义识别，失败自动降级 Regex（7/20 上线）
- **关键教训**：7/15 反馈"PI 识别错误 / 信息不全"时纯关键字识别不稳，上 AI 后准确率大幅提升。但**AI 不是替代规范输入，而是兜底不规范输入**——同期推动业务方"规定 PI 格式"，两条腿一起走
- **复用提示**：AI 用在"输入不可控"的环节；可控环节（能规定格式、能要 Excel 原件）优先做规范，成本更低更稳

### 6.4 能拿结构化源文件就别走 OCR

- **教训**：PI 用 PDF OCR 提取时把日期提取进了收货人地址、地址也不完整（0702 反馈）；改用 .xls 识别后准确率大幅提升
- **复用提示**：动手前先问业务方一句"**这个文件的原件是什么格式、能不能给 Excel**"。OCR 是最后手段，不是首选

### 6.5 OnlyOffice：编辑用编辑器，生成用转换服务

- **做法**：在线编辑走 OnlyOffice 编辑器（JWT + 单端口代理 + 模板占位符）；文档转 PDF 走 Conversion API
- **踩过的坑**：批量生成 PDF 最初用 Windows COM 调用，把部署锁死在 Windows 且不稳定，8/27 才改为 Conversion API（并发转换、失败自动回退 docx）
- **复用提示**：**转 PDF 一开始就上 Conversion API，不要碰本地 Office COM**。这是本项目部署层面最大的一次返工

### 6.6 静态配置 → 数据库（数据治理）

- **教训**：用户、包装规格、成分映射、翻译对照最初散在 JSON 里，后来出现配置缺失与不一致；8/1 一次性迁入 SQLite（7 张新表）
- **复用提示**：**配置从第一天就放数据库**，别从 JSON 起步。手写迁移脚本务必顺序编号（本项目已积累 18 个），后续接 Alembic 也方便

### 6.7 悲观锁 + 文档版本化（并发与追溯）

- **做法**：订单级锁（编辑期间锁定，防多人同时改）；文档用内容哈希幂等去重 + 版本号版本链
- **复用提示**：只要有多人同时用，锁和版本就是刚需，后补成本远高于一开始设计

### 6.8 /health 自检 + 审计装饰器（运维与治理）

- **做法**：`/health` 检测外部依赖（API / OnlyOffice / 数据库 / OCR 引擎）；审计用**统一装饰器 + 中间件**覆盖写操作（8/31 一次性覆盖 30 个接口）
- **踩过的坑**：审计最初只记登录名、无具体操作内容，且逐接口手写导致覆盖率低；8/31 重构为装饰器模式时，顺带发现批量上报端点的代码 bug
- **复用提示**：**审计一开始就做成装饰器 / 中间件**，逐接口手写必然漏；外部依赖必须有 `/health`，否则部署后排查全靠猜

## 七、踩坑清单（按模块自检）

> 全部来自本项目 5 个月真实业务反馈（2607 / 2608 / 2609 问题反馈文件）。复用这套技术栈时，逐条对照——**这些坑会跟着技术栈一起被复用**。

### A. 数据录入 / 解析

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 粘贴来源差异 | 企微在线表格用 8 空格分隔（空列丢失、后续列整体左移）；单元格内换行把一行截断成两行；行首片段未合并 | 见第五章完整复盘；列数校验前置 + 来源纳入测试矩阵 |
| 规格 ≠ 实际装入量 | 125KG 桶只装 120KG，毛重另算为 126KG（0702） | 包装计算要支持"每桶实际装入量"独立录入（7/16 已加） |
| 同产品拆多行 | 3000kg 拆成 1000+2000 两行 | 不要自动折叠去重，保留拆行、金额按数量分摊（8/5） |
| 描述文本被误当主键 | 内编提取时把销售订单表里关于内编的描述文本也提出来，导致重复行（0820） | 主键提取要排除上下文化的描述字段 |

### B. 单据 / 文档生成

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 行数上限 | 报关单限制 6 个产品（0803）；发票 / 箱单同样需要扩展（8/14） | 见 6.1，动态扩展是默认值 |
| 公式引用不随扩展重算 | 合同页公式只覆盖前 8 个产品（8/14） | 扩展后同步重写公式引用与合并单元格 |
| 中英文规则 | 币制要中文（美元 / 人民币，不用 USD/CNY，0803）；指运港写中文；装运口岸要中英对照 | 建"字段级中英对照规则表"，不要散在代码里 |
| 单复数 | PALLET / PALLETS 随数量变化（7/29） | 单位做单复数自适应 |
| 默认值 | CIF 运费保费一般 USD；默认币制从 CNY 改为 USD（8/27） | 默认值问业务方要"最常见那一种" |
| 多抬头 | 同一套单据要切换宏昊 / 民浩两套抬头、税号、印章（0821） | 模板参数化：公司代码驱动抬头 + 占位符 + 印章 |

### C. 主数据 / 对照表

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 对照表别名缺失 | 成分名"山梨醇"匹配不上、空格差异导致 MSDS 翻译错误（0722） | 对照表支持**别名 + 模糊匹配**，空格差异要归一化 |
| 缺记录静默回退原文 | 港口无记录时，贸易国 / 运抵国直接输出英文（0826） | 缺记录要么补字典，要么**显式提示"未匹配到，请确认"**，绝不静默输出原文 |
| 成分数据不完整 | 含量总和 ≠100%、CAS 缺失，导致 MSDS 一直误判为新配方、无法导入（0831） | 入库即校验：含量总和必须 100%、CAS 与组分成对必填 |
| 只有城市名没有国家 | 目的港填 Tashkent，运抵国被填成了城市名（8/26） | 补城市 → 国家映射字典兜底 |

### D. 台账 / 数据维护

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 台账只进不出 | 合并后没有修改按钮，没点合并下次要重录（0716） | 台账从一开始就开放增删改——业务数据是活的 |
| 编辑保存不生效 | 产品明细的报关成分等字段修改丢失（0831） | 编辑保存要做端到端回归验证，不能只测新增 |
| 数据量大后检索困难 | MSDS 台账条目多了翻不到（8/27 才补分页） | 列表页默认带分页 + 搜索 |

### E. 环境 / 部署

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 依赖 Windows 组件 | 批量生成 PDF 用 COM，锁死 Windows（8/27 才改造） | 见 6.5，用 Conversion API |
| 路径硬编码 | 跨平台（Windows / Linux）路径问题（6/25） | 统一路径处理，部署前在目标环境实跑一遍 |
| 外部依赖不可见 | OnlyOffice / 数据库 / OCR 挂了不知道 | `/health` 多组件自检（6/27 上线） |

### F. 业务规则本身（不是技术问题，但最耗时间）

外贸单证的规则极其细碎——0725 一次提了 20+ 条：价格条款只取方式不取城市、报关删掉运输方式与监管方式、签约日期自动取 PI 日期、保险除 CIF 为卖方其余写买方、箱单件数统一用"件"、装运期自动填生成日期……

**应对三条**：

1. **让业务方一次性列全规则清单**——一次问出 20 条，比上线后被逐条反馈 20 次便宜得多
2. **规则配置化**，不要散落在代码里——8/21 双公司模板、8/13 按 HS Code 动态字段都是这个方向
3. 接受"规则会持续微调"，把改规则的成本做低（配置 > 代码）

## 八、交付节奏与价值量化

### 8.1 演进节奏（本项目实测）

| 阶段 | 周期 | 目标 | 本项目对应 |
| --- | --- | --- | --- |
| 最小数据链路 | 第 1 周 | 数据能进来、看得见 | 5/28–5/31：解析 → 合并 → 台账 → 包装计算 |
| 单据自动化 | 2–3 周 | 能生成可用单据 | 6/1–6/23：OnlyOffice 集成 → MSDS 自动生成 → 正式交付船务部 |
| 增强与治理 | 持续 | AI 增强、数据治理、审计 | 7/20 AI 解析 → 8/1 数据层重构 → 8/31 审计覆盖 |

**规律**：先让业务用起来（6/22 交付 MSDS 生成），再在真实反馈里迭代。**不要追求一次做全**——本项目 98% 的功能里，相当一部分是交付后根据 18 条一线反馈补出来的。

### 8.2 价值量化（可直接用于汇报）

- **效率**：单笔含 3 个产品的 PI 订单，人工约 20 分钟 → 系统约 10 分钟（**提速约 50%**），且**产品越多增益越大**
- **覆盖**：44 天统计窗口内 6 名业务人员使用，有效合并记录 60 条，T/T ¥118,405.75 + L/C ¥137,110.00
- **闭环**：18 条一线反馈，多数已闭环（见 2607 / 2608 / 2609 问题反馈文件）

### 8.3 汇报话术（补充第一章）

> 这类项目的价值不只在"省了多少时间"，更在于三点：① **可量化的提效**（20 分钟 → 10 分钟，产品越多越明显）；② **全闭环交付**（需求对接 → 开发 → 培训 → 迭代，一个人跑通全程）；③ **可复制**——第二、第三个部门直接复用同一套栈，本次踩过的坑不再重踩。

**风险提示话术**（对业务方要提前讲）：

> 工具做出来 ≠ 用起来。上线后必然有一段"反馈密集期"（本项目交付后 2 个月内收到 18 条反馈），要提前安排好对接人和响应节奏；否则容易出现"用了但没形成习惯"的悬空状态，价值就停在纸面上。
