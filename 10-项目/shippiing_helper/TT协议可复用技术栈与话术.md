# TT 协议可复用技术栈与话术

> **缘起**：2026-08-04 总经办周会方总点评、邓楚羿指示——"TT 协议的这种应用可以梳理出框架，在需求池里面，以及后续在需求收集的过程中，更快判断有没有可以复用的场景。"
>
> **本文是轻量版**：一段可复制的判断话术 + 一套已验证的技术栈，直接粘进需求池套用。
>
> **来源项目**：`[[shippiing_helper]]`（TT 协议自动化 / 船务助手，98% 闭环）

---

## 一、可复用的一段话（需求池判断话术）

> **当业务部门提出"想做个工具把某项重复工作自动化"时，若命中以下特征，即可复用 TT 协议（船务助手）已验证的技术栈快速搭建，不必另起炉灶：**
>
> ① 业务规则明确但散落在 Excel / Word / PDF；② 内部用户少（≤10 人）但操作高频；③ 数据敏感、不出境；④ 需多数据源合并；⑤ 需反复生成单证 / 报表。
>
> **典型长相**：已有 SOP 但靠人肉执行，每天 / 每单重复"录入 → 计算 → 生成文档"。
>
> **投入**：1 名全栈 + 1 名业务接口人，1 周跑通最小数据链路 → 2-3 周单据自动化 → 持续 AI 增强。

这段话可直接作为需求池「同类需求识别标准」或向领导汇报时的标准表述。

## 二、可复用技术栈集合（TT 协议已验证）

| 层 | 技术 | 角色 | 复用提示 |
| --- | --- | --- | --- |
| 后端 | Python + FastAPI + SQLAlchemy + Pydantic | 接口 / 业务 / ORM | SQLite 起步，高并发再换 Postgres |
| 前端 | Vue3 + TypeScript + Vite + Pinia + axios | Web 界面 | 后端 StaticFiles 单端口托管 `frontend/dist` |
| 数据 | SQLite + 手写迁移（或 Alembic） | 存储 | 用户少足够；迁移脚本务必版本管理 |
| 文档 | OnlyOffice Document Server | 在线编辑 / 导出 Word·PDF | JWT + 单端口代理 + 模板占位符填充 |
| AI | DeepSeek API | 语义识别 / 模糊匹配 | 优先 AI，失败降级 Regex 兜底 |
| 解析 | PyMuPDF / python-docx / openpyxl / pytesseract | PDF·Word·Excel·OCR | 多格式入口统一收口 |
| 鉴权 | JWT + 简化 RBAC | 登录 / 权限 | 用户少够用，别上复杂权限中台 |
| 运维 | `/health` 多组件自检 | 部署后健康检测 | api / onlyoffice / database / tesseract |

**一句话技术栈**：`FastAPI + Vue3 + SQLite + OnlyOffice + DeepSeek`

## 四、何时不套这套（反向信号）

- 高并发（100+ 人同时操作）→ 推 SaaS 或独立后端架构
- 移动端 / 多端适配 → 推供应商或独立前端团队
- 多租户 / 复杂权限（角色 > 5 个）→ 推供应商系统（宏昊AI助手）
- 数据可公开 / 弱合规 → 走通用 SaaS 工具
